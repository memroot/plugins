# Memroot for Grok Build

This is the complete, self-contained Memroot plugin root, version `0.9.1`. The native agent plugin manager installs this folder from the public Memroot plugin marketplace and owns subsequent updates. Node.js is the only runtime requirement. Every script in `scripts/` is generated from the Memroot CLI source and bundled with its dependencies; no script refers to `npx`, the npm cache or files outside this bundle.

The memroot-status skill and `node scripts/status.mjs` explain this release's capabilities. Setup registers the production MCP server with Grok at user scope (`grok mcp add --scope user --transport http memroot https://api.memroot.dev/mcp`); its tools provide retrieval and automatic saving. Authorize it once inside Grok: run `/mcps`, select memroot and press `i` to sign in in the browser. Grok runs the OAuth flow itself and keeps the tokens in its own store (`~/.grok/mcp_credentials.json`); Memroot never reads or copies them. Setup preserves an existing `memroot` entry that differs, and `grok mcp remove memroot` removes the registration. Grok also reads the `memroot` server that Claude Code setup wrote to `~/.claude.json`, but it still needs its own authorization in `/mcps`. Setup also installs a global instruction file, `~/.grok/rules/memroot.md`, that names Memroot the default durable memory layer for every session.

Hooks read bounded native envelopes and metadata only, never transcript content or the network. The project in use is the one selected on this computer (`~/.memroot/project-selection.json`); no per-session state decides it. The session reminder (PostToolUse, once per session) adds one line naming the selected project and its `project_id`, or the exact command to select one, and, once an account is signed in on this computer, starts a detached background check that selects the account's only project when none is selected. The PreToolUse project guard stays silent for unrelated tools. Grok calls Memroot tools through `use_tool`, so the guard reads the arguments nested in that wrapper: it approves a Memroot memory call that names the selected `project_id`, denies one with a missing or different `project_id` with the id to retry with (Grok's support for rewriting tool input is unverified, so it never relies on a rewrite), and denies the call with the command to select one when nothing is selected. It also approves the read-only Memroot tools (`connection_status`, `projects_list`, `memory_request_schema`) with or without a selected project. Capture triggers (SessionEnd, PostCompact, Stop and the idle-prompt Notification) queue a job only after you agreed to the current capture terms, record the project selected when they fire, and start the detached bundled worker; a turn end queues a capture after 8 turn ends or 20 minutes, the idle prompt at most every 5 minutes (an idle prompt inside that window is remembered and queued by the next turn end once the window has passed), and work queued while no project is selected waits for the first selection. Capture only reads turns written after it was turned on. Jobs hold identifiers, paths, the project scope and a turn cursor, never raw text.

The bundled worker reads only the referenced session transcript, keeps user and assistant text plus tool names and file paths (never tool output), redacts secrets, personal email addresses and home paths locally and fails closed, runs your own agent CLI headless with no tools to propose memories, validates them, and sends only typed memories labeled session-extracted (not user-attested) to `https://api.memroot.dev/mcp` with the separate Memroot CLI capture connection. Each memory includes up to 3 short evidence quotes (at most 200 characters) from the redacted transcript, repo-relative paths and symbols, the normalized repository remote, and salted hashes of the session id and quoted segments; one retrieval query per capture contains only the repository name. Raw transcripts are never uploaded. At most 50 memories per capture run and 2,500 per rolling 24 hours; the service enforces your plan's memory limit. A later capture of the same session reads only the turns added since the previous one. `memroot capture off` stops capture and deletes queued work.

Grok ignores stdout for passive hook events, including SessionStart, and discards UserPromptSubmit output, so this bundle declares a PostToolUse hook for the session reminder (timeout 3 s), a second PostToolUse `memory-mirror` hook that tells Grok to save the same lesson to Memroot each time it writes its own built-in memory, through a file tool or a shell write into `.grok/memory/` or `.grok/rules/`, or to select a project first when none is selected (non-blocking, once per identical write in a session, no event content echoed), a SessionEnd hook (timeout 5 s; it typically returns in about 25 ms), a PostCompact hook with a 5 s timeout that runs the same script once a compaction is done (Grok treats PostCompact as a passive event that blocks nothing), and Stop and Notification hooks (timeout 5 s) that queue a debounced capture at a turn end or an idle prompt. For a Grok session the worker reads `updates.jsonl`, which Grok only appends to; `chat_history.jsonl` is rewritten at every compaction and is excluded from project-scoped capture; unavailable append-only updates fail safely. Grok also loads the Claude Code plugin from `~/.claude`. When both plugins are installed they share the name `memroot` and Grok 1.0.46 loads only the Claude Code copy, so the Grok session reminder (and with it the project line) is not delivered; the machine-wide project selection still applies, because it does not depend on which copy runs. A user-level `~/.grok/hooks` entry that does not depend on which plugin copy Grok loads is the planned follow-up. The reminder is emitted once per session and is not emitted again after Grok compacts the conversation, so a long session can lose it. It uses the documented Claude-compatible plugin manifest. From 0.8.1 a third PostToolUse hook, `failure-nudge` (matcher `Bash|run_terminal_command`, timeout 3 s), adds one line when a terminal command fails: this may be a known failure, so before reporting or fixing it check Memroot with `memory_retrieve` using the error code or symptom, not the output. Grok fires PostToolUse, not PostToolUseFailure, for a command that exits non-zero, and its `toolResult` (alias `tool_response`) is the structured `{"type": "Bash", "exit_code": N, ...}`; the hook nudges when `exit_code` is not 0 and skips a truncated result (a plain string), a background start (`BackgroundTaskStarted`, no exit code) and every other tool. The output and the command are never echoed, logged or stored. It fires once per distinct failure (a salted hash of the exit code and the command's first word) and at most five times a session, only with a project selected and the MCP server registered, never in a subagent, the capture worker or a `memroot import` run, and always exits 0 (Grok drops `additionalContext` from a hook that exits non-zero). Grok runs every PostToolUse hook and delivers each one's `additionalContext` in order, so the session reminder, the memory mirror and the failure nudge do not displace each other. Like the session reminder, it is not delivered when Grok loads only the Claude Code copy of the plugin. Grok gets no PreCompact or SubagentStop hook: its docs leave the subagent payload undocumented (ADR 0008). Grok also gets no `recall-check` hook (0.9.0: SubagentStart context, recall state, recall gate): Grok documents neither what a SubagentStart hook's output does nor the UserPromptSubmit payload the gate's prompt count needs. Grok receives the 0.9.0 recall wording (recall guidance v2) through its skill, the session reminder and the MCP text.

Inspect the installed plugin through the agent's native plugin interface.

Select the project once with the project skill (Claude Code: `/memroot:project`; Codex: `$memroot-project` or `/skills`; Grok: select `memroot-project` in the native skill picker) or with the command the session context gives. Use `status`, `list`, `use [NAME]` or `create NAME`. The selection applies to every session and agent on this computer until you change it. `use` with no name keeps a still-valid selection or selects the account's only project, and never picks one of several; the agent may run it on its own when nothing is selected and asks you when there are several projects. Several repositories may share one project, and a folder never selects one. Project commands use the separately authorized Memroot CLI connection and do not change capture.
