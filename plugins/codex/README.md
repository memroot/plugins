# Memroot for Codex

This is the complete, self-contained Memroot plugin root, version `0.11.0`. The native agent plugin manager installs this folder from the public Memroot plugin marketplace and owns subsequent updates. Node.js is the only runtime requirement. Every script in `scripts/` is generated from the Memroot CLI source and bundled with its dependencies; no script refers to `npx`, the npm cache or files outside this bundle.

Codex plugin support is a Codex feature and must be enabled. If `codex plugin list` fails or setup cannot find the plugin manager, run `codex features enable plugins` and restart Codex, then re-run `npx memroot@latest setup`.

The memroot-status skill and `node scripts/status.mjs` explain this release's capabilities. Setup registers the production remote MCP server with Codex and opens native OAuth sign-in when needed. The MCP tools provide retrieval and automatic saving after authorization. Setup also maintains a managed `<!-- memroot:start -->` … `<!-- memroot:end -->` block in `~/.codex/AGENTS.md` (or `AGENTS.override.md` when that file is used) that names Memroot the default durable memory layer; content outside the markers is untouched.

Hooks read bounded native envelopes and metadata only, never transcript content or the network. The project in use is the one selected on this computer (`~/.memroot/project-selection.json`); no per-session state decides it. SessionStart (`startup`, `resume`, `clear`, `compact` and `fork`) adds one line naming the selected project and its `project_id`, or the exact command to select one, and, once an account is signed in on this computer, starts a detached background check that selects the account's only project when none is selected. The PreToolUse project guard stays silent for unrelated tools. With a project selected it approves every Memroot memory call (`memory_retrieve`, `memory_create`, `memory_archive`, `memory_restore`) and sets its `project_id` to the selected project, so memory works without a permission prompt. With nothing selected it denies the call with the command to select one. It also approves the read-only Memroot tools (`connection_status`, `projects_list`, `memory_request_schema`) with or without a selected project. Capture triggers (SessionEnd, PreCompact, PostCompact, Stop and a SessionStart `resume`) queue a job only after you agreed to the current capture terms, record the project selected when they fire, and start the detached bundled worker; a turn end queues a capture after 8 turn ends or 20 minutes, and work queued while no project is selected waits for the first selection. A forked session (SessionStart `fork`) records where the copied history ends, so that history is never captured again. Codex has no idle event, so an idle session is captured at its next turn end, compaction or session end. Capture only reads turns written after it was turned on. Jobs hold identifiers, paths, the project scope and a turn cursor, never raw text. A PostToolUse `memory-mirror` hook tells the agent to save the same lesson to Memroot each time it writes its own built-in memory (a patch or a shell write into `~/.codex/memories/` or the Codex home `AGENTS.md`), or to select a project first when none is selected; it is non-blocking, nudges once per identical write in a session and echoes no event content. A UserPromptSubmit `prompt-nudge` hook reminds the agent on every prompt that Memroot is the project's primary memory (the agent's own memory is a partial copy), that it is checked at the start of each task and again whenever the work moves to another component, file area or failure, and that durable lessons are saved to Memroot without asking (recall guidance v2, 0.9.0). It classifies the prompt in memory and adds nothing for a Memroot project command (`memroot project ...`, `/project`, "use project X", "switch project"), a greeting, thanks, "anything else?" or a request not to check; it is non-blocking and never logs, stores or echoes prompt content. From 0.9.0 each nudge opens with a line of session facts (which prompt this is, and when Memroot was last checked) and names the selected `project_id`, and the hook counts the session's prompts in a per-session recall state (`<state>/recall-state/`, one 0600 file per session named by a salted hash, four integers: prompts, the prompt of the last Memroot check, checks, the last skipped prompt; removed after 14 days), which the nudge and the recall gate read. The `recall-check` hook (0.9.0, timeout 3 s) handles three events: SubagentStart gives every subagent a short factual Memroot context with the selected project's name and `project_id` (or that none is selected), because subagents see neither the SessionStart context nor the prompt nudge; PostToolUse on `memory_retrieve` records that Memroot was checked during the current prompt; and PreToolUse on `apply_patch`, `Edit`, `Write` or a `Bash` command that changes files or the repository is the recall gate: when no Memroot check happened since the latest prompt, the first such call is held once with a factual reason (the user's setup, the `project_id`, the pending `memory_retrieve` call), and a retry of the same call always goes through, so the gate never loops. The gate never acts on read-only tools, on a skipped or "don't check" prompt, without a selected project, in the capture worker or in a `memroot import` run. It reads only the event name, the tool name and, for `Bash`, the command to classify it; nothing is stored or echoed.

The bundled worker reads only the referenced session transcript, keeps user and assistant text plus tool names and file paths (never tool output), redacts secrets, personal email addresses and home paths locally and fails closed, runs your own agent CLI headless with no tools to propose memories, validates them, and sends only typed memories labeled session-extracted (not user-attested) to `https://api.memroot.dev/mcp` with the separate Memroot CLI capture connection. Each memory includes up to 3 short evidence quotes (at most 200 characters) from the redacted transcript, repo-relative paths and symbols, the normalized repository remote, and salted hashes of the session id and quoted segments; one retrieval query per capture contains only the repository name. Raw transcripts are never uploaded. At most 50 memories per capture run and 2,500 per rolling 24 hours; the service enforces your plan's memory limit. A later capture of the same session reads only the turns added since the previous one. `memroot capture off` stops capture and deletes queued work.

The SessionStart hook supplies a short static context about retrieving memory first and saving durable lessons automatically (timeout 3 s). The SessionEnd hook has Codex's maximum 3 s timeout and typically returns in about 25 ms. The PostCompact hook has a 3 s timeout and returns as fast; it runs after the compaction is done, prints nothing and exits 0, which Codex does not treat as a request to stop (only `continue: false` on standard output is). The Stop hook has a 5 s timeout, prints `{}` (Codex expects JSON from a Stop hook that exits 0) and only queues a debounced job, so it never asks Codex to continue. The PreCompact hook (new in 0.6.0, timeout 5 s) queues the same capture before the compaction; it prints nothing and exits 0, so it never blocks the compaction, and the PostCompact run after it finds no new turns. Codex only appends to the rollout file, so the turns from before a compaction stay in it. From 0.8.1 a second PostToolUse hook, `failure-nudge` (matcher `Bash`, timeout 3 s), adds one line when a shell command fails: this may be a known failure, so before reporting or fixing it check Memroot with `memory_retrieve` using the error code or symptom, not the output. Codex has no failure event and passes no exit code to hooks: for `Bash` its `tool_response` is the command's output as one string, a shape Codex does not document (codex-rs rust-v0.163.0). The hook therefore reads a failure only from strong signatures in that output (for example `command not found`, `npm error`, `ERR_PNPM_`, `error TS1234:`, `Traceback (most recent call last):`, a test runner's summary with at least one failure, or the `Node.js vX.Y.Z` line of an uncaught Node error), never from the words "error" or "failed" alone or a bare `Error:` line, and when the command only prints file or search content (`cat`, `grep`, `rg`, `git log`, ..., also after `cd ... &&` or inside `bash -lc '...'`) only from the shell's or the program's own error line; a work command piped into `tail`, `head` or `grep` is read in full. A numeric `exit_code` or `status`, should Codex ever send an object, decides alone. The output is matched in memory and never echoed, logged or stored. It fires once per distinct failure (a salted hash of the matched signature and the command's first word), at most once per turn and five times a session, only with a project selected and the MCP server registered, never in a subagent, the capture worker or a `memroot import` run. The heuristic is re-checked at every Codex release (ADR 0008, addendum "failure recall for Codex and Grok"). Codex has no subagent capture: a SubagentStop probe was not possible in an isolated home (ADR 0008).

After installation, review and trust SessionStart, UserPromptSubmit, PreToolUse, PostToolUse, SessionEnd, PreCompact, PostCompact, Stop and SubagentStart through `/hooks` in Codex. Installation does not establish hook trust. PreToolUse was new in 0.2.0; the PostToolUse `memory-mirror` and UserPromptSubmit `prompt-nudge` hooks are new in 0.3.0, and after a plugin update Codex lists them as untrusted and skips them until they are trusted there — the same `codexHookTrustStep` note printed by `memroot setup`. The Stop and PreCompact hooks are new in 0.6.0 and need the same trust step, as does the PostToolUse `failure-nudge` hook new in 0.8.1: it is a second PostToolUse entry, so after the update Codex keeps running the trusted `memory-mirror` hook and lists `failure-nudge` as untrusted until it is trusted in `/hooks` (`memroot doctor` reports PostToolUse as partly trusted until then). The `recall-check` hook new in 0.9.0 is a third PostToolUse entry, a second PreToolUse entry and the only SubagentStart entry; the earlier entries keep their index and trust, and Codex skips the new ones until they are trusted (`memroot doctor` reports PostToolUse and PreToolUse as partly trusted and SubagentStart as not trusted until then). Codex gives a subagent's tool calls the parent session id and no `agent_id`, so the gate treats a Codex subagent's calls as the session's. PreToolUse approves Memroot memory calls with the selected `project_id`, or denies them when nothing is selected, and approves the read-only Memroot tools; it does not act on any other tool. `memroot setup` and `memroot update` print a compact reminder to restart Codex and review new or changed Memroot hooks in `/hooks`. Hook commands use `PLUGIN_ROOT`.

Setup owns the single user-scope `memroot` MCP registration; this plugin intentionally declares no second MCP server.

Inspect the installed plugin through the agent's native plugin interface.

Select the project once with the project skill (Claude Code: `/memroot:project`; Codex: `$memroot-project` or `/skills`; Grok: select `memroot-project` in the native skill picker) or with the command the session context gives. Use `status`, `list`, `use [NAME]` or `create NAME`. The selection applies to every session and agent on this computer until you change it. `use` with no name keeps a still-valid selection or selects the account's only project, and never picks one of several; the agent may run it on its own when nothing is selected and asks you when there are several projects. Several repositories may share one project, and a folder never selects one. Project commands use the separately authorized Memroot CLI connection and do not change capture.
